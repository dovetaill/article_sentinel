# 管理后台界面重构设计文档

## 1. 设计背景

当前 `web/admin` 已具备关键词规则、检测任务、风险结果、操作日志、内容整改等业务能力，但整体视觉仍停留在一期占位壳层：

- 页面骨架与 `shadcn-admin` 参考站差距较大，缺少清晰的左侧导航、顶部工具栏和统一内容容器。
- 文案大量使用英文或直译表达，不符合中文业务系统的阅读习惯。
- 表格、表单、抽屉、弹窗的视觉语言不统一，无法形成“专业后台”的稳定感。
- 当前头图与强调方式偏演示稿，不适合政府融媒体机构的正式使用场景。

本次重构只调整前端样式层、文案层和页面呈现层，不改变后台接口、页面路由语义和业务信息架构。

## 2. 设计目标

### 2.1 总体目标

在保留现有业务结构和交互能力的前提下，将后台界面整体重构为接近 `shadcn-admin` 的现代后台样式，同时完成适配政府融媒体机构的中文化与正式化表达。

### 2.2 具体目标

1. 页面骨架接近参考站：左侧导航、顶部栏、内容区、卡片和表格的层级关系统一。
2. 所有页面改为自然、稳重、正式的中文表达，不出现翻译腔或中英混杂。
3. 视觉风格贴合政府融媒体机构：庄重、清朗、可信赖，而非互联网营销后台。
4. 保留现有业务模块：关键词规则、检测任务、风险结果、操作日志、内容整改。
5. 不改动服务请求层与业务流程，仅重写壳层、页面结构、样式和展示组件。

## 3. 设计边界

### 3.1 本次范围

- 重写后台整体布局与导航样式。
- 调整全局主题色、字体、阴影、圆角、边框、间距体系。
- 调整页面标题、按钮、状态、表单字段、弹窗标题等所有中文文案。
- 重构页面级呈现组件，使其风格贴近参考站并形成一致的视觉规范。
- 保持现有接口、参数、数据模型、路由路径和页面入口。

### 3.2 不在本次范围内

- 不新增业务模块。
- 不调整后端接口。
- 不改变关键词、任务、结果、日志、整改的核心交互流程。
- 不对信息架构做产品级重组。
- 不引入复杂的新业务状态或可视化图表需求。

## 4. 信息架构与导航方案

### 4.1 一级导航

保留现有业务结构，一级导航调整为以下中文名称：

- `关键词规则`
- `检测任务`
- `风险结果`
- `操作日志`

### 4.2 非常驻页面

- `内容整改` 继续作为结果页的后续处理入口，不单独常驻一级导航。
- 结果详情继续以抽屉/侧栏形式展示，保留现有信息密度和处理路径。

### 4.3 顶部栏

顶部栏承担页面定位与系统态信息展示，不承载营销式横幅功能。建议内容包括：

- 当前栏目名称
- 一句简洁正式的栏目说明
- 平台名称：`融媒内容安全巡检平台`
- 组织信息或值班状态占位

## 5. 视觉语言

### 5.1 整体调性

整体气质定位为：`庄重、清朗、克制、可信赖`。

- 版式参考 `shadcn-admin` 的现代后台结构。
- 风格不做潮流化、炫技化、营销化处理。
- 通过排版、边框、留白和组件统一性建立专业感。

### 5.2 色彩体系

采用浅底色为主的正式后台方案：

- 主背景：纸白 / 冷灰白，保持通透、整洁。
- 主色：黛青蓝，用于导航选中态、主按钮、关键信息强调。
- 主文字：墨灰，保证正文阅读稳定。
- 次文字与分隔：灰蓝、浅灰蓝。
- 点缀色：少量赭金，用于摘要、提示或品牌感强调，不大面积使用。
- 风险色：
  - 低风险：青绿
  - 中风险：赭黄
  - 高风险：规范红

### 5.3 字体体系

- 正文采用清晰稳重的中文黑体栈，提升可读性。
- 标题采用更有秩序感的中文标题字重，不使用花哨字体。
- 文案长度控制在业务系统习惯范围内，避免英文式长句翻译。

### 5.4 组件气质

- 卡片：浅底、细边框、轻阴影、中等圆角。
- 表格：表头清楚、行距舒展、强调信息层级。
- 表单：分组清楚、字段规整、说明克制。
- 弹窗/抽屉：像“业务处理面板”，不是营销弹层。
- 动效：仅保留必要的淡入、切换与 hover 反馈。

## 6. 中文文案规范

### 6.1 文案原则

- 全部使用自然中文。
- 保持正式、准确、平稳，不写口号化句子。
- 避免生硬直译，例如：`Rule deck`、`Hit stream`、`Audit trail` 等表达必须移除。
- 按政府融媒体场景修正文案语气，使用“规则维护”“任务发起”“结果处置”“日志留痕”“提交复核”等表达。

### 6.2 页面级命名

| 原表达 | 调整后 |
| --- | --- |
| Keywords | 关键词规则 |
| Tasks | 检测任务 |
| Results | 风险结果 |
| Logs | 操作日志 |
| Rectify | 内容整改 |
| New Task | 新建任务 |
| Detail | 查看详情 |
| Batch Offline | 批量下线处置 |

## 7. 页面设计说明

### 7.1 关键词规则页

目标是体现“规则维护中心”的稳定感：

- 页面头部展示标题与说明：统一维护巡检词库、匹配范围与处置建议。
- 主体为表格卡片，强调规则名称、规则分类、风险等级、适用范围、启用状态。
- 新增/编辑通过统一样式弹窗处理。
- 表单字段使用正式中文：所属机构、关键词名称、规则分类、匹配方式、风险等级、建议处置、适用范围、备注说明。

### 7.2 检测任务页

目标是体现“任务发起与执行概览”：

- 顶部加入概览卡，展示任务总量、执行中、已完成、命中总量等摘要。
- 列表强调任务编号、执行状态、扫描统计、发起人、创建时间。
- 详情抽屉改为更稳重的信息面板样式。
- 新建任务页采用“主表单 + 提示侧栏”布局，突出任务范围、扫描条件和执行提示。

### 7.3 风险结果页

目标是形成“结果处置中枢”：

- 顶部加入摘要统计与快速筛选区。
- 主表格突出文章标题、风险等级、处置状态、命中次数、命中片段。
- 批量操作条独立呈现，但避免过强警示感。
- 按钮统一为：查看详情、下线处置、进入整改。
- 详情抽屉采用分栏信息与标签体系，提高审阅效率。

### 7.4 操作日志页

目标是突出“审计留痕”：

- 页面顶部为规整筛选条。
- 表格字段中文化为：文章编号、任务编号、操作类型、状态流转、摘要说明、操作人、操作时间。
- 快照弹窗风格参考档案阅览层，突出可读性和可追溯性。

### 7.5 内容整改页

目标是体现“整改工单”而非 CMS 编辑器：

- 页面分为原文信息区与整改编辑区。
- 原内容采用只读信息卡片展示。
- 编辑区表单保持正式字段命名：整改标题、整改摘要、整改正文。
- 提交按钮调整为：保存整改、保存并提交复核。

## 8. 技术实施策略

### 8.1 技术原则

- 保留 `web/admin/src/services/*` 请求层。
- 保留 `react-router-dom` 路由路径与业务入口。
- 尽量减少对业务逻辑的侵入，仅调整页面容器与展示组件。
- 通过共享 UI 组件与设计 token 统一页面风格。

### 8.2 推荐实施方式

采用“样式层重构 + 页面结构重写”的混合方案：

1. 重写 `App.tsx` 和路由元数据，替换现有演示型头图。
2. 建立新的共享壳层组件、页面头部组件、摘要卡片、状态标签、内容卡片。
3. 分页重构业务页，保持接口调用和业务交互不变。
4. 逐页修正测试，确保中文文案与交互行为同时稳定。

## 9. 验收标准

### 9.1 视觉验收

- 整体骨架明显接近 `shadcn-admin` 的后台结构。
- 所有页面视觉语言统一。
- 界面气质符合政府融媒体机构使用场景。

### 9.2 文案验收

- 不再出现英文导航、英文标题或翻译腔说明。
- 栏目名、按钮、弹窗、状态、字段全部使用正式自然中文。

### 9.3 功能验收

- 现有页面路由、接口请求、核心交互保持可用。
- 关键词新增/编辑、任务发起、结果批量处置、日志筛选、整改提交等能力不回退。
- 现有测试通过，或同步更新测试后通过。

## 10. 实施结论

本次重构采用“保留业务结构，只重做样式与页面呈现”的策略：

- 业务上不重新发明后台，只把现有业务页面纳入一套统一、正式、接近参考站的后台壳层中。
- 视觉上不照搬海外模板的轻快气质，而是在其结构基础上落成更适合中文政务融媒体语境的表达。
- 实现上优先重写壳层和页面级展示组件，确保改造结果既接近参考站，又不破坏现有系统稳定性。
